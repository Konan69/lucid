# Grok Bot 0.39: auth and design evidence

This report treats the reconstruction as evidence, not as an invitation to fill gaps. `PROVENANCE.md` says the immutable release is the product specification and requires an inspectable artifact anchor for each recovered behavior (`~/refs/grok-bot-0.39-reconstructed/PROVENANCE.md:17-29`). The release is Grok Bot 0.39.0, upstream package `sand` (`~/refs/grok-bot-0.39-reconstructed/PROVENANCE.md:3-11`).

## Auth and identity

### Cursor account sign-in

The top-level Cursor account flow is a browser hand-off plus polling. `startLogin()` creates `/loginDeepControl` with a generated PKCE-like challenge/verifier pair, UUID, `mode=login`, `redirectTarget=sand`, and `supportsSelectedTeamLogin=true` (`~/refs/grok-bot-0.39-reconstructed/frontend/src-main/main-app/ea6-sand-error-mapping.ts:433-443`). Main opens that URL with `shell.openExternal`, then polls `/auth/poll` with the UUID and verifier until the response contains `accessToken` and `refreshToken` (`~/refs/grok-bot-0.39-reconstructed/frontend/src-main/main-app/ea6-sand-error-mapping.ts:445-475`; `~/refs/grok-bot-0.39-reconstructed/frontend/src-main/main-app/ea6-sand-error-mapping.ts:584-595`). The browser wait is deadline-bound; the default is five minutes (`~/refs/grok-bot-0.39-reconstructed/frontend/src-main/main-app/ea6-sand-error-mapping.ts:577-582`; `~/refs/grok-bot-0.39-reconstructed/frontend/src-main/main-app/ea6-sand-error-mapping.ts:276-277`).

### Token storage and secure-storage degradation

Cursor credentials are main-process-owned. The store is `${app.getPath("userData")}/sand-secrets.json`; logical keys are `cursor-access-token`, `cursor-refresh-token`, `cursor-selected-team-id`, and `cursor-accounts` (`~/refs/grok-bot-0.39-reconstructed/frontend/src-main/main-core-mc5.ts:597-610`). The disk file is ordinary JSON, written through a temporary file and rename; it is not SQLite or `electron-store` in the recovered implementation (`.../main-core-mc5.ts:778-808`). **Unknown — no artifact anchor** for any other Cursor-token store.

When Electron reports OS encryption available, values are passed to `safeStorage.encryptString()` and `safeStorage.decryptString()` and base64-wrapped (`.../main-core-mc5.ts:654-663`; `.../main-core-mc5.ts:745-761`). Saved account records keep encrypted access and refresh values plus encrypted profile metadata; the list projection returns account IDs and profile fields, not tokens (`.../main-core-mc5.ts:1035-1074`).

When secure storage is unavailable, the implementation calls `NN()`, stores the credential in the main-process `sessionSecrets` map, and removes the corresponding disk value; the warning explicitly says the token is memory-only and will not survive restart (`.../main-core-mc5.ts:666-673`; `.../main-core-mc5.ts:995-1005`). `noteSecretsUnavailableSession()` reports a `keychain_unavailable` settlement after successful authentication (`.../ea6-sand-error-mapping.ts:1464-1468`; `.../ea6-sand-error-mapping.ts:1509-1527`). On Linux, a detected `basic_text` backend is explicitly opted into plain-text encryption; the artifact does not establish that this is keyring encryption (`.../main-core-mc5.ts:643-655`).

A separate user-secrets capability exists for connector/environment secrets. Its durable store and persistence mode are distinct from Cursor auth; its exact implementation is in the helper-process slice (`.../ea3-helper-process.ts:810-873`; `.../ea3-helper-process.ts:881-959`). Do not confuse that API with the Cursor token store.

### Renderer projection and main-only credentials

The preload auth projection exposes status, login/add/switch/remove/logout actions, login-flight reads, profile/avatar actions, team reads/writes, and status/flight/team subscriptions (`~/refs/grok-bot-0.39-reconstructed/frontend/src-preload/preload.ts:2439-2537`). The declared main method table has no Cursor-token-returning method (`.../preload.ts:1983-2018`). Main has internal `peekAccessToken()` and `exportTokens()`, but they are not included in the exposed `desktop.cursorAccount` object (`.../ea6-sand-error-mapping.ts:995-1007`; `.../preload.ts:2439-2537`).

The renderer receives a projection with `kind`, `authId`, email, expiry, display name, profile picture, and profile readiness; logged-out state is a separate projection with cause/error fields (`~/refs/grok-bot-0.39-reconstructed/frontend/src-0.39/app/m16-stores.tsx:5408-5421`). Its store reads status and login flight, rejects stale freshness values, and consumes `cursor-auth-changed`/`cursor-login-flight-changed`; it never receives the access/refresh pair (`.../m16-stores.tsx:5513-5588`; `~/refs/grok-bot-0.39-reconstructed/frontend/src-0.39/app/m18-entry.tsx:3380-3394`).

### Backend authentication, refresh, expiry, and logout

The Connect interceptor resolves required versus anonymous mode, obtains the access token, and asks the team getter with `expectedAccountScope` derived from the token subject (`~/refs/grok-bot-0.39-reconstructed/frontend/src-main/main-app/ea4-rpc-trace.ts:353-381`). Authenticated requests carry `authorization: Bearer <access-token>` and, when resolved, `x-cursor-team-id`; every request also carries a machine checksum, client type/version, Sand box namespace, ghost-mode, request ID, lineage, and optional inference/workload headers (`.../ea4-rpc-trace.ts:383-422`). The transport is Connect over HTTP/1.1 (`.../ea4-rpc-trace.ts:442-451`).

JWT payload parsing reads `sub`, `email`, and `exp`. Account scope is SHA-256 of `sub` (or the raw token fallback), and refresh is selected when expiry is within 300 seconds or when the configured backend uses the development auth flow (`~/refs/grok-bot-0.39-reconstructed/frontend/src-main/main-app/ea4-model-and-sand-headers.ts:145-187`; `.../ea4-model-and-sand-headers.ts:199-219`). Refresh is a POST to `/oauth/token` with `client_id`, `grant_type=refresh_token`, and `refresh_token` (`.../ea6-sand-error-mapping.ts:1556-1585`).

Transient refresh failures retain the session for later retry. Repeated failure, an invalid/`shouldLogout` response, or a policy refusal advances the auth epoch, revokes credential use, clears profile state, and publishes a logged-out status; a newer rotated pair can rescue a rotation race (`.../ea6-sand-error-mapping.ts:1601-1622`; `.../ea6-sand-error-mapping.ts:1633-1704`). User logout removes stored access, refresh, and selected-team values, then best-effort POSTs `/auth/logout` with a Bearer token; the revoke request has a 15-second deadline and reports failure rather than blocking forever (`.../ea6-sand-error-mapping.ts:1237-1241`; `.../ea6-sand-error-mapping.ts:1276-1292`; `.../ea6-sand-error-mapping.ts:1294-1348`).

### Account, organization, team, and workspace scope

The auth scope is account-plus-team, not one generic workspace ID. `accountScopeOfToken()` hashes the JWT subject, while selected-team reads are keyed to that account scope (`.../ea4-model-and-sand-headers.ts:156-167`; `~/refs/grok-bot-0.39-reconstructed/frontend/src-main/main-core-mc5.ts:935-951`). The team-selection machine fetches memberships and the stored selection together, falls back when the selected team is no longer eligible, writes the replacement, mirrors it to the host, announces it, and may reload account state (`~/refs/grok-bot-0.39-reconstructed/frontend/src-main/main-app/ea1-auth-and-rpc-edge.ts:345-380`; `.../ea1-auth-and-rpc-edge.ts:590-611`). Scope changes block stale reads; selection writes are serialized and token-scoped (`.../ea1-auth-and-rpc-edge.ts:597-607`; `.../ea1-auth-and-rpc-edge.ts:706-730`).

The ordinary request path resolves team ID against the same token-derived account scope and sends it as `x-cursor-team-id` (`.../ea4-rpc-trace.ts:353-360`; `.../ea4-rpc-trace.ts:413-420`). Profile and team APIs use the same tuple of access-token getter, team getter, and machine ID (`~/refs/grok-bot-0.39-reconstructed/frontend/src-main/main-app/ea4-account-api.ts:53-58`; `.../ea4-account-api.ts:72-95`).

Organization IDs appear in device-management sign-in policy, alongside allowed team IDs, login emails, and login domains; the policy is serialized as `x-cursor-mdm-signin-policy` (`.../ea4-account-api.ts:555-685`). No ordinary organization request header is evidenced: **unknown — no artifact anchor** for direct organization-header semantics. “Workspace” is present in UI/integration vocabulary, but it is not shown as the Cursor auth scope in these artifacts (`~/refs/grok-bot-0.39-reconstructed/frontend/src-0.39/side/onboarding-flow.tsx:179-243`).

## Electron boundary

### Declared IPC/RPC table

The renderer-side table is `declareRpcEdge("main", ...)`; each method is declared with `noArgs` or a schema-backed `args` validator. The table includes shell controls, theme/update settings, auth/team methods, telemetry, persistence, secrets, MCP, and Chrome-cookie operations (`~/refs/grok-bot-0.39-reconstructed/frontend/src-preload/preload.ts:1820-2036`; `.../preload.ts:2037-2160`).

| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Declaration        | `rpcMethod()` accepts `noArgs` or field validators/Standard Schema; invalid declarations throw; `declareRpcEdge()` freezes the descriptor (`.../preload.ts:281-312`).                                                                                                                                                                                                              |
| Payload validation | Validators cover strings, finite numbers, booleans, literals, optional/nullable/union values, arrays, records, objects, and `Uint8Array` (`.../preload.ts:115-270`).                                                                                                                                                                                                               |
| Channel            | Renderer calls use `dune-rpc:<edge>:m:<method>`; events use `dune-rpc:<edge>:e:<event>`; probes use `dune-rpc:<edge>:probe` (`.../preload.ts:320-347`).                                                                                                                                                                                                                            |

### Window and navigation

The main `BrowserWindow` uses `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`, a resolved preload, and `webviewTag: true` (`~/refs/grok-bot-0.39-reconstructed/frontend/src-main/main-core-mc5.ts:169-195`). It loads either the configured dev URL or local `renderer/index.html` (`.../main-core-mc5.ts:198-201`). Window bounds/maximize state persist in `userData/window-state.json` with atomic writes (`.../main-core-mc5.ts:81-106`; `.../main-core-mc5.ts:117-165`).

Navigation opens new windows externally and denies them. Main-frame navigation is allowed only when origin and pathname remain the same; subframes must be approved or be the Sand HTML-preview path (`.../main-core-mc5.ts:202-224`).

Titlebar options are platform-specific: macOS uses a framed `hiddenInset` titlebar with traffic-light position `{x: 16, y: 15}`; Windows uses frameless `hidden` titlebar plus `titleBarOverlay`; other platforms use frameless `default` titlebar (`~/refs/grok-bot-0.39-reconstructed/frontend/src-main/main-core-mc4.ts:1814-1820`; `.../main-core-mc4.ts:1975-1986`).

### Deep links, singleton, updates, notifications

Packaged, non-lab builds install a single-instance lock and register deep-link protocol clients. The concrete schemes are `grokbot` and `sand`, authority `app`; recovered routes are `bot-template`, `plugin-add`, `open`, `settings`, and `sidebar` (`~/refs/grok-bot-0.39-reconstructed/frontend/src-main/main-core-mc6-entry.ts:891-938`; `~/refs/grok-bot-0.39-reconstructed/frontend/src-main/main-core-mc1.ts:2367-2424`). Initial argv, `open-url`, and `second-instance` activations are queued until the renderer announces readiness (`.../main-core-mc1.ts:889-1003`).

The updater exposes idle/checking/available/downloading/staging/ready states, verifies downloaded Windows installer signatures, and restarts to apply a ready update (`~/refs/grok-bot-0.39-reconstructed/frontend/src-main/main-app/ea3-secrets-store.ts:218-303`; `.../ea3-secrets-store.ts:849-947`). The filename is a reconstruction slice label; the cited code is the updater class in that file. OS notification decisions are driven by `agent-needs-input` and `agent-done` transitions, then suppressed for hidden/disabled agents, focused windows, or the five-second throttle (`~/refs/grok-bot-0.39-reconstructed/frontend/src-main/main-app/ea3-connector-protocol.ts:1573-1651`). Agent events feed both OS notifications and dock badges (`.../ea3-connector-protocol.ts:1446-1477`). Sound preferences and `notification-sound` events are separately bridged (`~/refs/grok-bot-0.39-reconstructed/frontend/src-preload/preload.ts:474-486`; `.../preload.ts:2583-2586`).

## Motion

The 0.30 cross-check records three spring families: soft ambient `{stiffness:100,damping:10,mass:1}`, snappy UI `{500,25,1}`, and heavily damped drift `{1,63,1}`. It also records 100, 200, 250, 450, and 800 ms duration buckets (`~/agency/vivid/refs/grok-bot-0.30/motion/motion.ts:9-17`). Named CSS curves include dominant ease-out-expo `cubic-bezier(.22, 1, .36, 1)`, ease-in-expo, ease-out-quint, ease-out-circ, and a soft ease-out-back (`.../motion.ts:18-24`). The transition inventory is dominated by 100/150 ms color, opacity, border, and transform changes, with a 200 ms box-shadow transition; `none` is also present (`.../easings.json:2-50`).

The 0.39 onboarding reconstruction shows explicit motion intent: landing and waking use `none`, meet uses `bounce`, computer-demo uses `slow`, jobs uses `standard`, and leaving a scene uses a 300 ms `exit` transition (`~/refs/grok-bot-0.39-reconstructed/frontend/src-0.39/side/onboarding-flow.tsx:1354-1438`; `.../onboarding-flow.tsx:1492-1528`). The renderer reads `window.matchMedia("(prefers-reduced-motion: reduce)")` (`~/refs/grok-bot-0.39-reconstructed/frontend/src-0.39/app/m3-components.tsx:3217-3224`).

The avatar is a state machine rather than one spinner. Lifecycle states include sleeping, waking, idle, listening, thinking, searching, and working; product states include spawning, loading, sending, receiving, uploading, notifying, and alerting (`~/refs/grok-bot-0.39-reconstructed/frontend/src-0.39/app/m3-components.tsx:2319-2372`). The cross-check records randomized hold ranges, 2.5 s progress and 2 s spawning minimums, 300 ms pose cross-fade, and a 1.5 s global minimum (`~/agency/vivid/refs/grok-bot-0.30/avatar/states.ts:44-76`). CSS keyframes cover fades, translation/scale entrances, shimmer, rotation, warning flashes, bobbing, and anchor flashes (`~/agency/vivid/refs/grok-bot-0.30/motion/keyframes.css:520-550`; `.../keyframes.css:638-738`; `.../keyframes.css:956-974`).

## Interaction states

### Onboarding

The default path is `landing → meet → computer-demo → jobs → tools → create`; role selection inserts `role`, and the onboarding-bot flag removes `create` (`~/refs/grok-bot-0.39-reconstructed/frontend/src-0.39/side/onboarding-flow.tsx:384-417`). The landing renders the sign-in card; an already signed-in user advances rather than starting login again (`.../onboarding-flow.tsx:4980-5015`; `.../onboarding-flow.tsx:5180-5209`). The rendered cases cover landing, meet, computer-demo, jobs, role, tools, create, and hand-off (`.../onboarding-flow.tsx:5250-5319`).

Completion is account-bound. Hand-off waits for computer readiness, checks whether the account is already onboarded, then provisions the flagged onboarding Bot or creates a configured teammate, marks onboarding seen, and completes; the operation carries the current account slot and aborts on account change (`.../onboarding-flow.tsx:2885-2917`; `.../onboarding-flow.tsx:5136-5188`). The hand-off UI receives computer state, readiness, error, retry, and pull percentage (`.../onboarding-flow.tsx:5308-5320`).

### Main conversation

The activity vocabulary distinguishes thinking, working, web search/browsing, file reading, drafting, command execution, computer work, waiting on a command, waiting on another Bot, and `waiting_for_you` (`~/refs/grok-bot-0.39-reconstructed/frontend/src-0.39/app/m4-components.tsx:3480-3630`). Agent live state separates `is_running`, `is_composing_message`, `is_retrying`, optional activity, and optional awaiting-user state; client state separately carries unread count, last activity/message, notification settings, and sidebar visibility (`~/agency/vivid/refs/grok-bot-0.30/protos/GrokBotService.proto:687-725`).

The activity slot maps running plus composing to `typing`, running without composing to `working`, and neither to `none`; activity text and elapsed time are passed to the transcript row (`~/refs/grok-bot-0.39-reconstructed/frontend/src-0.39/app/m13-components.tsx:5356-5429`; `.../m13-components.tsx:6633-6680`). Status dots use `working`, `needs-attention`, `offline`, `error`, and `info`; a blocked marker selects `needs-attention`, while unread selects `info` (`.../m2-stores.tsx:2891-2907`; `~/refs/grok-bot-0.39-reconstructed/frontend/src-0.39/app/m3-components.tsx:344-382`).

| ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Assume a provider/device-code/password flow.                             | The desktop evidence proves only website hand-off plus polling; other top-level flows are **unknown — no artifact anchor** (`.../ea6-sand-error-mapping.ts:433-475`).                                                                                                   |
| Persist Cursor tokens when OS secure storage is unavailable.             | Grok Bot deliberately keeps them in memory for one session and deletes the disk value (`.../main-core-mc5.ts:838-845`; `.../main-core-mc5.ts:995-1005`).                                                                                                                |
| Treat every renderer frame as trusted.                                   | Main requires the trusted app window’s top frame and rejects untrusted senders (`.../ea2-otel-tracing.ts:2214-2235`).                                                                                                                                                   |
| Collapse account, organization, team, and machine into one workspace ID. | The artifacts keep separate token-derived account scope, selected team, MDM organization/team policy, and machine checksum (`.../ea4-model-and-sand-headers.ts:156-167`; `.../ea4-account-api.ts:555-685`; `.../ea4-rpc-trace.ts:413-420`).                             |
| Use animation as the state model.                                        | The renderer has explicit `typing`, `working`, `waiting_for_you`, `needs-attention`, and error states; onboarding also deliberately uses `none` transitions (`.../m13-components.tsx:5356-5429`; `.../m3-components.tsx:344-382`; `.../onboarding-flow.tsx:1354-1406`). |
