# Runtime signals in a Thread

The phone drew Flue bookkeeping as a notice. At the baseline, `apps/mobile/src/data/message.ts:124` admitted every non-hidden record; `display: diagnostic` therefore passed. `signalSpeaker` at lines 77–80 classified any system message without a signal descriptor as `Speaker.Notice`, including successful instruction updates. The phone drew instruction-update text in the notice pill (`apps/mobile/src/screen/chat/Message.tsx:98`). Resource updates carrying an untagged descriptor reached `Speaker.Silent`, but the permissive filter still admitted their rows. This is a confirmed source-level cause; the production database was not accessed.

Flue 2.2.2 projects canonical `instructions`, `resources`, and `environment` records as `role: system`, `purpose: advisory`, `display: diagnostic`. Its public projection omits `signal` when the record has neither a tag nor attributes; resources carry `attributes.resource` and have an untagged descriptor. The installed `dispatch-BlxCz6iq.mjs` has the classification at lines 2352–2374 and the history/live projection at 2570–2595 / 2798–2823. Filtering only `hidden` misreads a diagnostic as product content. Unknown dispatch signals must also be silent unless the product names them.

Web already returned no content for a system record without a signal unless its settlement failed (`apps/web/src/screen/thread/Message.tsx:270`). Its permissive transcript filter still admitted the diagnostic rows, however, and did not share its policy with the phone. Desktop loads the same web renderer (`apps/desktop/src/main/window.ts:227`), so it must use the same shared policy.

The fix puts message visibility in the shared client state package and makes the phone and web consume it. System records are visible only for a Person’s `message` signal, the product’s `schedule` / `follow-up` wakes, or a failed settlement. Other signals are silent regardless of the runtime’s display hint. Ordinary user/assistant records retain their display policy; hidden records stay hidden. Failed notices retain the existing product rendering; no styling or copy changes are included.

The runtime was inspected rather than changed. `packages/agent/runtime/src/agents/vivid.ts:37` already uses day-granularity dates. Context is prepared and frozen for a response (`src/context.ts:239–256`), with a clock truncated to the hour (`:142`). The prompt can legitimately change between responses as the hour, notes, integrations or chosen name change. `run_code` uses a module-constant description (`src/tools/code.ts:13,92`). No unnecessary per-model-turn churn was established. Suppressing these records at their product projection also handles old persisted history and future runtime bookkeeping.

The phone change is JavaScript only; no phone native config, dependency, patch, version or binary changes are needed. The root lockfile changes only for the separate web DOM-test development dependency. Native interaction was not run. Focused public message-model tests and real-web rendering results are recorded in the pull request, including instructions, resources, a shared Person’s message, both named wakes, unknown signals and failed settlement. No runtime/server, database, deployment or migration was changed.

Verification: eight shared-source cases and twenty-four phone-model cases pass (32 total). The updated phone tests run against the original public message model fail three cases and pass twenty-one: instruction visibility, failed settlement with attributes, and the permissive unknown-signal filter. The real browser displays no instruction/resource text and does display the shared Person, named Watch and failed notice. A previous optimistic send remains in the fixture, so the row count includes it; these are transport fixtures, not production records. Desktop coverage is by its use of the same web renderer; Electron and native phone interaction were not run.

Confidence is high in the model/projection cause and public-test evidence. The phone’s failed notice retains its existing `textOf(message)` content, which can contain the runtime’s failure detail; copy is explicitly outside this scope. The instructions/resources update records themselves are silent. No prompt-churn reduction is claimed.
