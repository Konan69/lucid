# Typing and repeated submission investigation

Branch: `fix/web-typing-and-double-send`. Baseline: `9779f0261ab1655d25bc33b7b47f53edcfa8788f`. Measurements: 10 October 2026.

**Typing: confirmed React/state causes fixed; an animation paint cost remains.** At the baseline, `apps/web/src/screen/Thread.tsx:229` subscribes to every Flue snapshot; lines 249–253 filter the transcript and rebuild its context, and line 178 maps every row. `screen/thread/Message.tsx:87` had no memo boundary. Each streamed delta therefore renders every historical row, even while the Person types in an unrelated input. `screen/thread/Layout.tsx:81–110` also rebuilds its children at face/writing changes. Historical Markdown is memoised and does not reparse at each key; the active reply reparses at each delta.

A composer key writes `draft.keep` (`Composer.tsx:107–116`). The baseline `data/drafts.ts:63,92,145` rereads, decodes, encodes and synchronously writes the entire draft document through `data/kept.ts:15–18`. Only Composer subscribes to the draft text. The Thread, sidebar and Markdown do not subscribe to it. Presence changes at the empty/nonempty edge, with a separate five-second heartbeat. `packages/client/state/src/sync.ts:31,93` debounces SaveDraft for 700 ms; it is not a server write per key. A save acknowledgement/watch update can notify the store, but an unchanged text snapshot does not render Composer again. These transport/subscription conclusions come from reading; the fixture measured browser storage and rendering, not production RPC traffic.

The textarea uses CSS `field-sizing-content`; no JavaScript scrollHeight/pre-paint measurement loop was found. Streamed values are not component keys: message ids are stable, and the conversation remount key changes only when first words land. Thread length amplifies streaming row work, while storage cost follows the total draft document (bounded to fifty places), not transcript length.

The fix memoises rows and their relevant message fields, keeps context/callback identities stable, and gives the textarea its own text subscription. Composer follows only the empty/nonempty edge, so BorderBeam no longer receives new children at each key/delta. Draft changes stay in memory, persistence is coalesced to 300 ms with page-hide/visibility flush and cross-tab absorption. Face rendering remains subscribed in Layout; its historical rows and Composer now bail out.

**Remaining cost and confidence.** Confidence is high in the history-render and storage mechanisms and their measured reduction. Input-to-paint medians while streaming did not improve in the normal headless runs. In a separate diagnostic only, pausing CSS animations reduced fixed ordinary-input streaming latency from 109.4 ms median / 117.0 ms p95 to 22.3 / 26.8 ms, with zero long tasks. The only active CSS animation found in that fixture was BorderBeam's spin/fade. This establishes a separate headless rendering cost, not its production magnitude. The animation was restored; changing motion/styles is outside the requested scope. It remains unresolved by this PR.

Other costs, ranked by the measured before-run aggregate, not invented per-key estimates:

1. Full transcript rendering while streaming: 2,449.7 ms React render work and fifty long tasks in the composer window; 1,623.3 ms and thirty-six tasks in the independent-input window. Fixed to 107.2 / 98.5 ms and zero tasks. Window lengths differ because the same twenty-key protocol completes faster after the fix.
2. Paint/animation work: 137.1 ms Paint CPU in the baseline composer streaming trace, 56.1 ms after; the diagnostic above isolates its remaining presentation delay. No appearance/motion change is included.
3. Layout/style work: baseline composer streaming trace contains 64.2 ms Layout CPU, five forced layouts and thirty-three synchronous style reads. Fixed: 22.8 ms, zero forced layouts and one style read. This includes normal CSS field sizing, not a JavaScript height loop.
4. Draft storage API work: 4.3 ms total for twenty reads and twenty writes in baseline composer streaming, versus 0.3 ms for four coalesced reads/writes afterward. Schema parsing/encoding happens around these API calls; its independent cost was not separately instrumented. A timer flush from prior composer typing can occur while the ordinary input is measured.
5. Draft reconciliation, fiber replacement for the 700 ms server debounce, transcript filtering/last-user lookup and active-reply Markdown parsing remain. Their separate durations were not measured; only their enclosing render/task work was measured.

**Repeated send: a web reentrant submission is reproduced and fixed.** Baseline `screen/thread/Composer.tsx:57–68` submits the message captured by the previous render, clears the external draft, then calls onSend. Three handler calls before React commits the emptied field still see the same captured text. `screen/Thread.tsx:277–279` allocates a new UUID for each call. While a reply streamed, three synchronous DOM Enter events produced three actual Flue POSTs with the same body and three distinct keys; after the fix, the identical probe produced one POST and an empty field. This reproduces a client capability, not the exact production event spacing (0.49 / 0.43 s), native key-repeat sequence, or database admission.

The new submit consumes the live draft synchronously once and rejects repeated Enter events. A file-only submission is also consumed once before repaint. The separate first-message path (`data/threads.ts:67,98` at baseline) sent without a key and retried without one; it now retains one key from composition through uncertain-response retries. Existing Thread “not sent” retries already retained their key. SDK send/RPC write paths do not automatically create fresh keys on reconnect; reconnect reobserves state. Mobile `Chat.tsx:304,333,418,472` and `data/delivery.ts:40` use pending state and retain the failed same-message key; no proven mobile triple-send path was found. These mobile/retry/reconnect conclusions are read-only.

The server is behaving according to its contract: `apps/server/src/threads/gateway.ts:149,189–194` derives identity from Person plus key (or creates one when missing), and `threads/runs.ts:297,326,344` checks fingerprint within that identity and permits the same Person to send while working. Different keys can therefore create different Runs with one fingerprint. Confidence is high in the demonstrated web vulnerability and fix; attribution of the October 9 production incident to this exact path remains unproved. No server deduplication or production data was changed.
