# Durable

Read the installed Pi Durable and AI SDK sources before changing their boundaries. Verify pinned APIs. Keep the bridge small. Use public extension points. Never patch Pi internals or SDK methods.

Pi Durable 1.0.4 copies the provider's partial message, including growing raw partialJson/partialArgs when retained. The watch can deliver those scratch fields in block/message updates. A block update is not a terminal block: anthropic-messages, openai-completions (late identity/customInput), bedrock-converse-stream and mistral-conversations mutate parsed arguments and scratch fields; openai-responses-shared replaces whole text/thinking at output_item.done; Google adds textSignature while text still streams. Only message_end closes blocks and permits final tool-input-available and approval. This library does not stream tool arguments yet. The source-derived provider wrapper and real SQLite proof are in fixtures/provider.ts and conformance/arguments.test.ts. Never approve a partial input or treat a document replacement as a provider end.

`@vivid/durable` is the Promise entry. `@vivid/durable/core` is the Effect entry. Verify the package exports before importing it. Both entries must share contracts and behaviour. Keep React and React Native UI out of this package.

Pi owns the transcript, inbox, submissions, tasks and replay policy. Never mirror Pi state into another store. The host chooses and authorizes the conversation. Ignore the client's supplied history. Decode wire input at ingress. Validate emitted chunks against the pinned AI SDK schema.

Watch before submitting. Buffer without waiting on the reader; replacement snapshots fail with WatchOverflowed and cancelled or closed watches fail with WatchClosed. Do not lose events between admission and attachment. Stream only the run answering that submission. Queued follow-ups get their own run and assistant message. Repeated request ids must not create another submission.

A hold's wait is volatile. Its settlement is durable. Register the wake before reading the settlement. The client stream parks; the run does not end. A decision must work without a client and after restart. A denied call never executes, and its reason reaches the model. The first settlement per Pi tool task wins. The pending live slot and beforeTool hook expose the same durable task id, including after recovery. Return detached settlement values. Reject answers for calls that are not waiting. Scope settlements to the actual call so reused ids cannot inherit approval.

Pi decides whether interrupted tools replay. The stored and current policies must both be safe to rerun. Unsafe interruption reaches the model as an error. Safe replay is not an exactly-once guarantee for external side effects.

Reconnecting combines durable state with later events and produces one assistant message per run. After a network error, an application reloads its messages from history and resumes with fresh SDK stream state; it does not resume into a kept partial message. The pinned SDK's reset-step clears only the current step, so replaying the whole run into a retained message in step 2 duplicates earlier text and tools. See ai/src/ui/process-ui-message-stream.ts getCurrentStepParts/reset-step/start and ai/src/ui/chat.ts makeRequest (852–882). Step 1 alone can reset the full retained prefix. Retry must discard failed partial parts. Person answers and parallel approvals work with the SDK's stock automatic-send predicates. All-parallel agents show generating calls in content order. Sequential-capable agents show only the first generating call; later calls and committed queued slots wait for tasks or results. The scoped live-document watch delivers queued task allocations, merged with the event watch. One pure presentation rule withholds later generating calls of sequential-capable agents and committed queued slots; duplicate input phases across both channels are suppressed. The sequential suite proves the stock approval predicate, mixed plain/held calls, denials, GET attachment and crash recovery.

Use the faux provider and fresh SQLite databases. Never use real credentials or shared app data. Register cleanup before the first write. Wait on streams, promises or durable state. Never sleep or poll in tests. Test Promise consumers through `src/main.ts` and Effect consumers through `src/core.ts`. Do not mock the seam under test. Cite the upstream file and test name above every ported case. Keep `it.fails` only where the lane brief explicitly permits a source-proven upstream limitation; otherwise fix the case and remove the marker.

Use one-word filenames, ESM, top-level imports and type-only imports. Avoid `any` and non-null assertions. Comment non-obvious ordering and failure behaviour. Pin any added dependency exactly. Keep optional platform dependencies out of core imports.

From this package, run `pnpm exec vitest run` and `pnpm exec tsc --noEmit`. To focus the ports, run `pnpm exec vitest run src/conformance`. From the repository root, run `pnpm exec oxfmt --check packages/agent/durable`. Run every changed case. Pi storage conformance uses the published runner; there is no package-supplied environment adapter. Flue's portable ordering and replay expectations are adapted, not its store interface. These Node consumer tests do not establish React Native transport conformance.

Holds are addressed publicly by opaque, schema-backed `HoldId` values derived from Pi tool tasks, not provider call ids. `waiting()` returns that id; direct `decide` and `answer` require it. Approval request/response chunks and decoded SDK `approval.id` retain it, so a stale decision cannot authorize a successor task even when the provider reuses an id. Receipts and unanswered later questions are keyed separately by hold id; late answers reserve the first output durably before admission and deduplicate on `answer:<holdId>:<attempt>`. `answers.ts` retains queued delivery receipts in `asked` until placement. Abort reopens withdrawn submissions; the next answer selects a new output under a fresh attempt; queued/placed repeats and different-output crash retries cannot change it. All successful answers return the settlement. `delivery.ts` owns the Open/Reserved/Submitted schema. Kind mismatches fail `CallNotWaiting`. Every resume must first match the current run message id, derived from its first input; stale cross-run resumes settle nothing. Client `addToolOutput` contains only a call id: HTTP ingress resolves it to the unique currently waiting answer hold, so replayed client outputs rely on provider call ids being unique within a run; approvals do not. With history, reload-then-resume also avoids chat.ts:852–858's snapshot of a retained input-streaming tool part.

`abort.ts` explicitly cancels the ordinary conversation run through `pi.ts`; stream cancellation only detaches observation. The abort suites prove partial text, interrupted approval waits and withdrawal of queued follow-ups. `src/examples/main.ts` and `src/examples/effect.ts` are backend server examples checked by the package TypeScript graph; maintain README excerpts from those sources. UI hook examples belong to the frontend owner.

`history.ts` pages raw fork-aware `Conversation.entries`, independent of model compaction. User ids are entry:<entryId>; one assistant stretch uses entry:<first assistant entryId>. Paging counts messages and never splits a stretch. Invalid wire/interior/foreign cursors fail HistoryCursorInvalid; non-positive or fractional limits fail HistoryPageInvalid. One shared desk reads plans, holds and unresolved transcript provenance once per page. Denial response chunks retain their durable reason. Public submission status locates the run in progress. History includes its placed user inputs and any users before its first assistant entry; GET reconnect supplies its assistant and tool results. A steer placed after that assistant stays out of history until settlement because reconnect cannot show it in order. Pi generation.js starts runs from placed inputs and only appends placed steer inputs. History skips system/reset/compaction/application entries; late answers are ordinary user messages for now, without answerTo metadata. Shared chunks/presentation and the AI SDK reader build the parts. `desk.ts` resolves plans and per-chunk task provenance so reused call ids retain their own receipts on replay; `reading.ts` is the narrow SDK iterator adapter.

The checked-in sequential observation case confirms the pending successor task allocation in the generation `tools` commit reaches both `Harness.watchDoc(LiveDoc)` and `Conversation.watch` as taskId operations. Around that commit `watchEvents` delivers c1's execution start/end and result-message events, then no c2 event before an appended receipt. The lower document channels do carry the change; the event channel lacks task-admission vocabulary. Changing observation is a separate design decision, not a polling fallback.

Promise callers validate their own wire hold ids with main.holdId(text), which throws HoldIdInvalid. Batch resume admission observes waiting once and shares it across decisions/outputs; commits still validate each exact task. Continuations require the assistant message id and known calls. Resolve the message's first input through its submission receipt and raw entry bounds before matching calls; never select a successor run by a reused call id. Live allocation frames may refresh holds but parking requires prior event settlement. Historical/reconnected chunks retain result-task provenance per chunk, never one newest-task mapping for every occurrence of a reused id.

N2 uses an explicit host policy. ToolsOptions.execution defaults to parallel and must equal HarnessSettings.toolExecution, which Pi keeps private. ToolsOptions.sequential names overrides that force whole-round sequencing. Every bridged registration carries executionMode explicitly and every plan carries the host declaration. readDesk combines agent registrations with these declarations: native registrations without a mode use the declared default; any sequential declaration across extensions is conservative. A sequential-capable agent presents only its first generating call per response, withholding later ones until tasks/results exist; all-parallel agents retain today's order. Never infer the hidden setting. conformance/mode.test.ts proves omitting the sequential declaration is misuse, not a supported configuration.

model.live.test.ts defaults to EXPLABS; DURABLE_LIVE_PROVIDER=openrouter uses Pi AI's own openrouterProvider and requires DURABLE_LIVE_MODEL from the installed catalogue. Only use credentials supplied for this work, never another tool's credential store. Auth stays with envApiKeyAuth/built-in provider support, never key inspection or logging. The catalogue determines the API, not the model's brand: anthropic-messages retains partialJson; openai-completions retains partialArgs. The approval tool requests a memo of about 150 words and always checks final input equality, approval order and exactly one approved execution. Truncated block changes and scratch presence are printed as observations; use the verbose reporter to see successful-test output. EXPLABS is capped at two requests per case and approval retries are disabled. The truncated-input regression is proven against the provider wrapper and, for openai-completions, against a real provider (old dispatch restored: the client saw `{ account: '' }`; current code passes). Other implementations are wrapper-only.

Settled history preserves provider content order. Any multi-call response of a sequential-capable agent, even a parallel round with an unused sequential tool, may append a withheld call after trailing text in live streams and early attachments, giving text/c1/text/c2 where history gives text/c1/c2/text. Pi generation.js startToolRound stores the assistant's provider order; finishToolRound deletes live.tools. No durable record retains per-reader presentation timing. conformance/ordering.test.ts proves the difference with the real stock SDK client; do not claim exact sequential part-order parity between history and live observation.

Aborted parsed partial tools produce SDK tool-input-error/output-error, not input-available or approval. Preserve these parts in history and replay. Empty provider tool ids/names never create a client part; reveal identity from a later block update in content-index order. Pi message_end also reports user entries: observations of a model response must end on pi.assistant, not the first message_end.

Ordered user text/file parts pass through one admission converter in input.ts. Only inline base64 image data URLs map to native Pi image blocks; remote URLs, non-image files, malformed base64 and media mismatches fail PartUnsupported before any watch/submission, with HTTP 400. Never fetch a file URL or drop a file silently. Filename is typed bridge metadata on the same image block: Pi submissions copies that JSON into pi.user unchanged, including queued inputs; history decodes it back to the SDK file part. No mirrored transcript or auxiliary filename store. Hosts bound request bytes before respond, and file counts/decoded sizes before typed respondTurn/core respond/prepareRun. Core Input turns carry parts; RunInput.content supports string or ordered InputPart values. conformance/pictures.test.ts proves real Chat HTTP, provider image input, persisted order/filenames, file-only core admission, reload and unsupported-part rejection.
